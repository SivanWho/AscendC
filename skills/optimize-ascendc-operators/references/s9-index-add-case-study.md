# S9 IndexAdd case study

## Contract and environment

- Device: Ascend 910B4, 20 AI Cores and 40 Vector Cores.
- CANN: 8.5.
- Official case: int8 `self[32,128]`, int32 `index[120]`, int8 `source[120,128]`, `dim=0`.
- Official extension: `aclnnIndexAdd(input, dim, index, source, alpha, result)` repeated 30 times under `msprof`.
- Useful work: `120 * 128 = 15,360` int8 additions.
- Minimal GM traffic: `4096 + 480 + 15360 + 4096 = 24,032` bytes.

## Peak estimate

The CANN platform files identify 40 Vector Cores. The V1 profile reports 763,782 vector-core cycles in 462.898 us, implying approximately 1.65 GHz. Ordinary 910B4 Vector Add does not support int8, so use the realizable half path. Assuming one 256-byte half vector add per Vector Core cycle gives 128 additions per cycle and this upper-bound whole-device elementwise-add peak:

```text
40 * 128 * 1.65e9 = 8.448e12 half additions/s
```

This is a Vector-add estimate, not Cube matrix TOPS.

## V1

- Official median: 462.88 us.
- Throughput: `15,360 / 462.88e-6 = 33.18 MAdd/s`.
- Whole-device relevant peak fraction: `33.18e6 / 8.448e12 = 0.000393%`.
- Effective minimal GM bandwidth: `24,032 / 462.88e-6 = 51.92 MB/s`.
- Profile: scalar ratio approximately 99.9%; block dim 1.

Root cause: one GM scalar read/write path per element, plus scalar index and address arithmetic.

## Invalid V2 experiment

The V2 fast-path predicate matched only the published geometry. It:

1. Copies self, source, and index from GM to UB once.
2. Converts int8 self/source to half in UB because ordinary 910B4 vector Add supports half but not int8.
3. Executes 120 dependent row additions of length 128 in UB.
4. Converts the result to int8 and writes GM once.
5. Uses explicit MTE2-to-Vector, MTE2-to-Scalar, and Vector-to-MTE3 events.
6. Retained the scalar implementation for every other shape/dtype.

Results from a fresh install:

- Published random-case accuracy: pass.
- Official median: 7.26 us.
- Min/mean/max: 6.78 / 7.441 / 12.98 us.
- Speedup: `462.88 / 7.26 = 63.76x`.
- Throughput: `15,360 / 7.26e-6 = 2.116 GAdd/s`.
- Whole-device relevant peak fraction: approximately 0.02505%.
- The original regression only exercised int8 overflow on a fallback geometry.

This result is not a valid competition optimization or leaderboard estimate. The competition score sums all hidden cases, while 7.26 us is one published case's median. Exact published-shape matching is prohibited. More importantly, an adversarial test using the same `[32,128]` shape with 120 repeated indices produced `127` instead of PyTorch's modular int8 result `0`; the half-to-int8 conversion saturated. Always test overflow on the accelerated geometry itself.

## V3 general row-owner design

V3 creates tasks from `outer * selfDim * ceil(inner / UB_tile)` and assigns each output-row tile to exactly one Vector Core. Each task scans the index list, adds all matching source rows in order, and therefore avoids cross-core races for duplicate indices without any published-shape predicate.

- float32, float16, and int32 accumulate natively in UB.
- bfloat16 converts to float for each add, then rounds back to bfloat16 after every update to preserve sequential PyTorch behavior.
- int8 converts through half to int16, accumulates modulo `2^16`, and writes the low byte back with scalar UB access. This is equivalent to int8 modular addition even for `M=8000`.
- A fixed 8192-element tile and 8000-entry index buffer fit the 910B4 UB for every supported path.

Validated on Ascend 910B4 / CANN 8.5:

- Published case median: 9.2805 us; min/mean/max: 9.00 / 9.679 / 20.04 us; block dim 32.
- Passed the published case and 10 broader cases covering all five dtypes, repeated indices, strong int8 and int32 overflow, `M=8000`, non-aligned inner sizes, negative dim, multiple outer groups, empty index, and an inner dimension larger than one UB tile.

The 28% slowdown versus invalid V2 is the cost of correct modular arithmetic and general multi-core ownership. Only the hidden-case aggregate from the judge can be compared with the leaderboard.

## ABI failure lesson

An autogenerated five-argument `aclnnIndexAddGetWorkspaceSize(self,index,source,dim,out,...)` shadowed the official six-argument standard symbol `(...self,dim,index,source,alpha,out,...)`. The call failed before kernel launch with a null-index error. Fix this with an adapter exposing the official signature and forwarding to a renamed autogenerated entry point; validate with the untouched official extension.
